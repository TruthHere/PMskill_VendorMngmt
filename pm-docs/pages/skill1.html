使用场景
这个 Skill 在什么情况下被触发、解决什么场景的问题
📋 场景描述

室内工装项目启动后，项目经理通过邮件转发将各直采包的关键文件（RFP、技术文件、合同、报价等）交给 Skill。Skill 在收到邮件的当下同步完成归档、结构化提取，维护企微在线表格 Tracker（每项目一张）与文件夹内的履约卡片 HTML，作为后续请款核验、变更分析、验收、结算的数据基座。

一个直采包对应一个已确定供应商、一般对应一封 RFP 邮件。变更、请款等后续事项由独立 Skill 处理；Skill 1 负责归档与结构化建档。

🎯 适用阶段

项目初始化（阶段 0）：发送项目初始化邮件（进度计划作附件），建立 Schedule 基座

邮件驱动履约（阶段 1）：从 RFP 邮件起，每转发一封邮件或文件，Skill 同步归档、提取、更新 Tracker 与卡片，贯穿采购谈判至项目结束

类型 典型例子 核心管理重点
纯供应 石材供应、灯具供应 到货数量 + 材料质量验收
供应+安装 木饰面供应安装、玻璃隔断 到货 + 安装进度 + 两阶段验收

📧 输入方式：邮件转发（非上传入口）

Skill 1 不设文件上传界面。所有输入均通过项目经理转发邮件（或发件 BCC）送达 Skill 专用邮箱。微信等渠道收到的文件，由项目经理整理后单独发邮件转发给 Skill。

项目经理与 Skill 的日常沟通（付款指示、补充说明等）：除 Skill 主动追问外，均由项目经理先发邮件给 Skill。

💰 付款条件（以合同为准）
来源 适用类型 输入方式 说明
合同提取 总包（及有合同的包） 转发合同邮件 → Skill 同步提取 付款节点、比例、罚款条款写入履约卡片，项目经理邮件确认准确性。总包滚动进度款、具体付款结构核验由 Skill 2 负责，不在 Skill 1 范围

约束：付款条件一律以合同为准；PO 不含付款条款。付款条件变动时，项目经理发邮件通知 Skill 更新，系统保留修改历史。

📎 支持的附件格式

邮件附件支持 PDF / Word (.docx) / 图片 (jpg/png) / DWG / Excel 等。Skill 收到后同步识别类型、归档、提取。

⚠️ 输入限制说明

1. 阶段 0 优先：必须先发送并处理项目初始化邮件，阶段 0 时 Tracker 中无采购包。项目编号一旦确定不建议修改。

2. 一包一供应商：一个直采包对应一个已确定供应商，一般对应一封 RFP 邮件，不会一封邮件询价多家。

3. OCR 依赖：扫描件/图片类附件依赖 OCR，准确率影响提取质量。

4. 变更 / 请款：Skill 1 仅负责归档；业务分析与核验由 Skill 2 / Skill 3 等独立 Skill 覆盖（含总包滚动进度款）。

📐 设计原则
1
邮件留痕优先 — 口头/微信约定必须通过邮件确认留痕；无邮件记录的条件标注「口头约定·需确认」
2
关键节点逐步转发 — RFP、顾问确认技术文件、Raise PO 等分别在对应步骤转发给 Skill，不是一口气批量转发；谈判报价修改、中间往来默认不归档。合同等额外文件可随时单独转发归档
3
收到即同步处理 — 每收到转发的邮件/文件，Skill 当下同步完成归档、提取、更新 Tracker 与卡片，并刷新采购包状态；不是先存档、之后再专门提取的两段式流程
4
人做决定，Skill 做搬运 — 撰写/发送邮件、定标、转发时机由项目经理决定；Skill 只读不写，不负责撰写或发送 RFP / Raise PO
5
能自动就不打断 — 归类、提取、入库默认自动执行；仅当 Skill 置信度低时，经企微对话机器人向项目经理确认
6
文件只归档一次 — 邮件附件提取后按标准命名存入对应子文件夹，避免微信/邮件/本地多处重复存放
7
卡片不具合同效力 — 履约条件卡片仅供参考辅助查阅，一切以原始合同/报价文件为准
阶段 0 项目初始化 · 1 步（所有采购流程的前置条件）
0
项目背景信息录入（项目初始化邮件）
在新项目启动时最先执行，一次录入、全程复用。是所有直采包、表单、提醒的数据锚点。
👤 人做什么
  • 撰写并发送项目初始化邮件至 Skill 专用邮箱
  • 邮件正文写明：项目名称、项目编号、项目类型、地址、甲方、项目经理、币种与含税约定
  • 邮件正文注明本地项目根文件夹路径
  • 将完整进度计划作为邮件附件（非逐字段手填日期）
⚙️ Skill 同步做什么
  • 解析初始化邮件正文 + 附件，提取项目背景字段
  • 从进度计划附件中提取项目级节点 + 各采购包相关节点（待具体调试）
  • 自动为项目生成 / 绑定 Skill 专用邮箱（待调试）
  • 在指定的本地路径创建项目根文件夹结构
  • 调用企微 API 自动创建在线表格 Tracker（每项目一张，初始无采购包行）
  • 将项目背景字段注册为全局预填源，供后续表单 Skill 调用
  • 建立项目 Schedule 基座，供直采包交期倒排和 R1 提醒
阶段 1 邮件驱动履约管理 · 从 RFP 起至项目结束

同步处理原则：项目经理每转发一封邮件，Skill 当下同步完成归档、提取、更新企微 Tracker 与履约卡片 HTML。不确定字段经企微对话机器人确认。

Skill 能力：邮件接收（转发 + BCC）+ 企微对话机器人（字段确认、节点提醒推送）。

分工原则：RFP / Raise PO 由项目经理自行撰写发送，Skill 只读不写。关键节点逐步转发（RFP → 顾问确认技术文件 → Raise PO），谈判报价修改不转发。合同等额外文件可随时单独转发。

Tracker：每项目一张企微在线表格（Skill 自动建表，经企微 API 自动写入），从第一封 RFP 转发起新增采购包行。详情见文件夹内履约卡片 HTML（可导出 PDF）。

里程碑：RFP 发出 → 技术方案已确认 → 商务报价已确认 → PO 已发起 → 已结算（Tracker 五列时间戳即状态，无单独状态下拉）

专用邮箱：支持转发或发件时 BCC。转发邮件中写清项目、采购包、供应商，Skill 从主题和正文识别（准确率待具体调试）。

💡 阶段衔接说明

阶段 0 结束标志：项目初始化邮件已发送并被 Skill 处理；本地根文件夹已创建，进度计划已解析，企微 Tracker 已自动建表（尚无采购包行）。

阶段 1 运行方式：从第一封 RFP 转发起在 Tracker 新增采购包行，同步归档、提取贯穿全程。步骤 1~4 为采购主线；步骤 5~6 在 PO 发出后持续运行（步骤 6 从步骤 1 起即生效）。

Skill 产出三样东西，各有不同用途
📋 输出 ①：Tracker（企微在线表格）

形态：每项目一张企微在线表格，每个直采包一行（总览）。由 Skill 在阶段 0 自动创建，后续经企微 API 自动写入（非手工复制粘贴）

内容：列名清单见 §6「Tracker 列名」；核心含采购包名称、供应商、对接人邮箱、类型、总金额、状态、交期摘要等

用途：全局俯瞰所有直采包状态。详情查阅文件夹内履约卡片 HTML。是 R1 全局风险预警的扫描对象

🏷️ 输出 ②：履约条件卡片（HTML → PDF）

形态：每个直采包一份可导出 PDF 的 HTML 卡片，放采购包文件夹根目录（模板：pm-docs/templates/fulfillment-card.html；字段示例见 pm-docs/templates/card-detail-reference.html）

更新机制：每次收到新邮件增量更新卡片字段，不全量重造

内容（描述，非样式）：

  • 通用信息：供应商名称、采购包名称、总金额（标注含税/不含税）、签约/报价日期
  • 付款节点：按类型展示（纯供应 3 个 / 供应+安装 5 个 / 顾问 4-5 个 / 总包合同提取基础节点）。总包滚动进度款及付款结构核验见 Skill 2。标注来源（合同提取 / 邮件指示）
  • 验收标准：数量验收、质量/安装验收、交付物验收（按类型有不同组合）。含特殊条件（如检测报告要求）
  • 约束条款：罚款条款（仅总包）、质保期、特殊条件
  • 数据来源：标注每个字段来自哪个文件；付款条件标注来源（合同提取 / 邮件指示）

定位：纯辅助查阅，不具合同效力；字段可由项目经理邮件确认或指示修正。底部标注「本卡片仅供参考，以原始合同/文件为准」

用途：日常管理时快速查阅某个包的履约条件，是 Skill 2/3/4/5 的数据基座

🏗️ Skill 运行架构（Agent 无关）

本 Skill 的核心交付物是 SKILL.md + 配套脚本/模板，与具体 Agent 平台解耦。同一套规则可在 Cursor、WorkBuddy 或未来常驻服务上运行。

推荐三档演进路径：

  • 档 A · 半自动（当前 MVP）：人在 IDE / WorkBuddy 中触发 Skill；邮件与企微由配套脚本轮询或 webhook 拉取；Agent 负责解析、写表、更新 HTML 卡片。
  • 档 B · 邮箱触发：专用邮箱收到邮件 → 队列任务 → 调用同一套 Skill 逻辑（无人工点运行）；企微确认仍走对话机器人。
  • 档 C · 常驻服务：独立 Worker 7×24 监听邮箱 + 企微回调；项目状态存本地 SQLite / JSON；Agent 仅处理低置信度或复杂提取。

🔍 邮件采购包识别

项目经理转发的邮件中会写清项目、采购包、供应商，Skill 据此定位 Tracker 行与文件夹。识别不准时经企微对话机器人确认。

💬 企微对话机器人：确认、提醒与写回

通道：企业微信对话机器人向项目经理推送；PM 在同一对话中回复，Skill 解析写回 Tracker 与卡片。

字段确认消息模板（建议）：

【Skill1 · 待确认】项目 SARL-P5 · 新邮件已收到 主题：Re: SARL-P5 · furniture · 施耐德 — RFP 识别事项：步骤1 · 发出 RFP 请确认或修正以下字段（直接回复序号+值，或回复「全部确认」）： 1. 采购包名称：furniture 2. 供应商：施耐德电气 3. 对接人邮箱：xxx@schneider.com 4. 采购包类型：供应 5. 归档：07_往来文件（正文）+ 02_图纸（附件×2） 回复示例： · 全部确认 · 2 供应商=施耐德（中国） · 取消（暂不处理）

节点提醒消息模板（建议）：

【Skill1 · 节点提醒】SARL-P5 · furniture · 施耐德 下一节点：到货验收（计划 2026-07-20） 里程碑：PO 已发起 · 付款节点 2/5 待触发 卡片：/Users/.../履约条件卡片.html

写回逻辑（实现层）：

  1. 每封待确认邮件生成 pending_id，与 Tracker 行 / 草稿卡片字段暂存关联。
  2. 机器人消息 footer 带 pending_id（或企微回调 msgid 映射）。
  3. PM 回复 → 企微回调 webhook → 解析意图：全部确认 / 字段序号=新值 / 取消。
  4. 确认后：调用企微 API 更新 Tracker 行 → 增量写入 HTML 卡片 → 归档邮件附件 → 关闭 pending。
  5. 低置信度识别：回复数字选择候选包 → 绑定后再走确认流程。
🏷️ 履约卡片：HTML 增量更新

模板：pm-docs/templates/fulfillment-card.html（占位符渲染）；样式参考 card-detail-reference.html。

增量原则：每次新邮件只更新本邮件影响的字段，保留已有正确字段与数据来源标注。付款节点变更保留历史来源（合同提取 / 邮件指示）。

导出 PDF：浏览器打开 HTML → 打印 → 存储为 PDF；后续可加 headless Chrome 自动化（非 MVP 必须）。

卡片中的验收标准是多方数据比对的基准。Skill 4 比对供应商报量、监理确认量、现场照片时，验收标准（数量允许偏差、质量指标）来自卡片。输出文件（验收一致性报告）归入 05_验收记录 文件夹。
S5
→ Skill 5 结算归集
卡片中的合同价 + 质保金比例 + 罚款条款是结算公式的输入。Skill 5 自动拉取该供应商全生命周期数据（合同价 + 变更 ± + 罚款 - 已付 - 质保金），生成结算单草稿。输出文件（结算单）归入 06_结算资料 文件夹。
R1
→ R1 全局风险预警
Tracker是 R1 每日扫描的对象。R1 设定规则（超期未请款、变更未评估、质保金异常等），每天扫描 Tracker 中所有采购包，把异常经企微对话机器人推送给管理人员。
R2
→ R2 供应商画像
Tracker + 卡片是画像的数据源。R2 为每个供应商自动生成合作档案（累计变更率、延误次数、一次验收合格率），下次招标时输出风险提示。
💡 关键依赖提示

Skill 1 是整条链的地基——Skill 2 和 Skill 5 直接依赖它的输出。如果 OCR 把付款比例提错了，或者口头约定的付款条件录错了，后续请款核验和结算全跟着错。因此落地时优先验证 OCR 准确率，并确保口头约定的付款条件录入后有复核习惯。
