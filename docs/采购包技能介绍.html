# 项目初始化（Skill 0 · new-project）

只把「空项目」立起来。**从 RFP 建包起**归 Skill 1。

| 做 | 不做 |
|----|------|
| 问齐必填 → `.skill/`、空的采购包状态表、`项目背景.md`、`项目档案/00_进度计划/`、`待处理邮件/` | 采购包 / 请款入账 / 变更 / 「已处理邮件」 / 从待处理邮件里建项 / 连邮箱 |
| 同一回合：有进度计划则按编排表 B；给了客户请款单 `.xlsx` 则交给 payment-sheet 认模板 | 自己填请款单、刷请款页、把认模板写进 `init_project` |

## 编排硬规则（摘要）

跨 Skill / 进度 / 合同 PDF / 邮件分发 → 先读 `<skills-root>/skill-orchestration/ALWAYS.md`（细节见同目录 `README.md`）。
`skills-root` = 本机 Skills 安装根（WorkBuddy 常见 `~/.workbuddy/skills/`）。命令写成 `python3 <skills-root>/<技能名>/scripts/…`。

## 怎么问

用户说新建项目后，**缺的必填一次性列出来**。没齐不要跑脚本、不要建文件夹。

必填：

| 问什么 | CLI | 没答 |
|--------|-----|------|
| 项目名称 | `--name` | 不建 |
| 项目编号 | `--code` | 不建 |
| 项目类型（实验室工装这种白话） | `--type` | 不建 |
| 项目地址 | `--address` | 不建 |
| 甲方 | `--client` | 不建 |
| 项目经理 | `--pm` | 不建 |
| 文件夹放在电脑哪 | `--root` | 不建 |
| 用什么币，金额含不含税 | `--currency` | 不建 |

币种和含税合成一句再传。用户说「人民币、含税」就写 `--currency "人民币 含税"`。没有默认值，禁止自己填成 `CNY 含税`。

必填齐了，再问两句。用户说「没有」就继续建，不卡：

- 有没有进度计划（有就在这次对话里给）
- 有没有客户请款单表格（只要 `.xlsx`）

**不要问**：邮箱、授权码、开票主体、分部号、甲方对接人、设计顾问、造价顾问、建筑面积、开工竣工、项目总价、总包、供应商名单。

进度计划和请款单在这次对话里收，不放进「待处理邮件」。

## 建项命令

先看目标文件夹里有没有 `.skill/project.json`。有的话脚本会拒绝，你先问：接着用这个项目，还是换一个空文件夹。接着用就不要再跑建项。

```bash
python3 <skills-root>/project-foundation/scripts/init_project.py \
  --root "/path/to/project" \
  --name "Sample Project" \
  --code "SAMPLE" \
  --type "实验室工装" \
  --address "上海市浦东新区 xxx" \
  --client "xxx 有限公司" \
  --pm "张三" \
  --currency "人民币 含税"
```

脚本不会删文件夹里原来的文件。已建过再跑，退出码 2，原因 `already_initialized`。

建完用户能看见的就是：`项目背景.md`、采购包状态表、`项目档案/00_进度计划/`、`待处理邮件/`。不建空采购包。变更台账等真有变更再出现。

1. 问齐再跑上面的命令。
2. **若有**进度计划：归档到 `项目档案/00_进度计划/` → **skill-orchestration 表 B**。没有就跳过。
3. 同一回合写出对人那一份时间线：`项目档案/00_进度计划/关键节点时间线.html`（没进度就先出空壳）。
4. 用户给了客户请款单 **`.xlsx`**：同一回合交给 **payment-sheet** 认模板（还没有采购包，不要 sync）。没给，或给了 `.xls` / Word：建项不阻塞，必须说「还没有请款单模板，请款单生成尚未启用」；不是 `.xlsx` 再加一句目前只收 `.xlsx`。禁止用技能自带样例充数。
5. 汇报：文件夹在哪、状态表在哪、`待处理邮件` 已建好。下一步告诉用户：可以把整封邮件另存进「待处理邮件」，然后说「处理待处理邮件」。建包后的关键节点仍是项目里那一份时间线，包级节点要当时补，不是现在、也不是建包脚本自动编的。

禁止写「建包后会自动同步时间线并补包级节点」。

# 合同履约结构化（Skill 1）

一句话：**从建包起**，把履约邮件变成 Tracker + 包文件夹 + 干净 `card-data`，再交给履约卡片 Skill 出 HTML。做到哪为止，见下面的表。

## 编排硬规则（摘要）

跨 Skill / 进度 / 合同 PDF / 邮件分发 → 先读 `<skills-root>/skill-orchestration/ALWAYS.md`（细节见同目录 `README.md`）。
单独使用功能 Skill 时禁止擅自串联履约/请款；脚本已串完的不要双跑；时间线对人只有 `项目档案/00_进度计划/关键节点时间线.html` 一份。
`skills-root` = 本机 Skills 安装根（WorkBuddy 常见 `~/.workbuddy/skills/`）。命令写成 `python3 <skills-root>/<技能名>/scripts/…`。

## 做什么 / 不做什么

| 做 | 不做 |
|----|------|
| 处理 `fulfillment.*` 邮件（或粘贴） | 项目初始化 → Skill 0 |
| 建包 / 更新 Tracker / 归档 `.eml` | 请款申报入账 → Skill 2 |
| 写出/更新 `card-data.json`，调用 vendor-card | 变更 / Change PO → Skill 3 |
| 搞不定的字段进 `pending.json`，再问人 | 手写 HTML；手猜进度日期 |
| | 代写 RFP、代发 Raise PO |

前置：`.skill/project.json` 已存在（否则先 Skill 0）。

## 主路径

优先走脚本（邮件已在盘上时）：

```bash
python3 <skills-root>/po-flow/scripts/process_email.py \
  --eml "/path/to/mail.eml" \
  --project-root "/path/to/project" \
  --route-json "/path/to/route.json"   # mail-inbox 分发时带上
```

对话里改数据后刷界面（`process_email` 内部已含则不必再跑）：

```bash
python3 <skills-root>/vendor-card/scripts/render_card.py \
  --package-dir "/path/to/{序号}_{采购包}_{供应商}/" \
  --patch '{"supplier_name":"…", …}'
```

收信入口是项目根 **`待处理邮件/`**（`mail-inbox` 的 `process_drop_folder.py`）。本 Skill 只消费分过来的 `fulfillment.*`。误投初始化/变更时 `process_email` 只拒收挂 pending（兜底，**不是**第二套分类器；防误伤真源在 mail-inbox）。这版不要教用户连邮箱。

**线程回信**：分类器只认关键词、不懂「这是回信」。`Re:` 里引用的原 RFP 常被判成 `fulfillment.rfp` + `confidence: high`。**high 不等于对。** Agent 必须读正文**最新一段**，按 mail-inbox 意图表覆写 `intent`，route.json 加 `"intent_verified": true` 再跑 `process_email`。不要另造分类器，也不要跟着错判再建一次包。脚本兜底：已建包 + 回信主题 + 仍判成 RFP → pending `possible_thread_reply`，等你覆写。

## 硬规则（短）

1. **先理解再处理**（全局）：见 `skill-orchestration`「全局原则」。本 Skill：先搞清步骤与附件再写 Tracker / `card-data`；脚本抽不出则打开附件读懂或 `pending`。回信按上面「线程回信」办。
2. **归档**：归属某包的邮件 → 整封 `.eml` 进 `07_往来文件/`。`01_合同报价/` 只放报价/合同，禁止签名动图。图纸：有 dwg/pdf/zip 进 `02_图纸/`；签名/inline 图跳过；**只有 Box/SharePoint 等链接时必须在 `02_图纸/` 留指针文件**（URL+密码），不要留空文件夹让人以为没图纸。不要擅自登录云盘下载。
3. **金额（附件为准）**：Tracker 必须有「不含税 / 含税」。**报价附件 > 邮件正文**。冲突 → 写附件并 `pending`（`amount_mismatch_body_vs_quote`）；有附件抽不出 → `quote_amount_unparsed`；两侧不全 → `tax_rate_uncertain`。
4. **对接人**：To/Cc/From 里供应商域名都收，`; ` 拼接。
5. **里程碑**（有时间戳=完成）：RFP 发出 → 技术方案已确认 → 商务报价已确认 → PO 已发起 → 已结算。Raise PO 同时打「商务报价已确认 + PO 已发起」。
6. **付款节点**：任意履约邮件正文能解析就写入 `card-data`（中+英）；合同/报价 PDF 先走 `read-pdf` 读正文，再由本 Skill `extract_contract_pdf.py` 抽节点候选。
7. **界面**：只维护 `card-data` → 调 **vendor-card**（出卡片，并自动调 **payment-sheet** 刷请款申请页）。`process_email` / `render_card` 已成功且有 `claim_form_path`（或 `did` 含 `payment-sheet.sync`）时，**同一回合不要再手跑** `render_card` / `payment-sheet` sync（除非脚本失败要补）。
8. **进度（与编排对齐）**：
   - 见到 `.mpp` / 甘特 / Master Schedule → 按 `skill-orchestration` 表 B：`mpp-to-excel` → **Agent 主导** `critical-nodes` → 再渲染卡片；**禁止手猜日期**。
   - `add_package` / `process_email` 建包后，脚本**最多**重渲**项目级**时间线 HTML：`项目档案/00_进度计划/关键节点时间线.html`（有已有 `critical_nodes` 时只重渲、不覆盖节点；尚无节点则 skip）。**不会**给这个新包自动补「到货」等关键节点。
   - **RFP 建包成功后（同一回合）**：Agent 必须把包名、类型、邮件里的交期/到货日交给 `critical-nodes`（按编排表 B）**merge** 该包节点；**不要**手改 `schedule.json`；**不要**再手跑 `analyze_schedule` 覆盖总包/已有推理。
   - 对人汇报只指项目档案那一份时间线；**不要**把包文件夹里的 `关键节点时间线.html` 当成交付物介绍。
9. **口径只看本项目 + 这封邮件**。不要翻本机其它旧项目的 Tracker / 文件夹来猜类型、节点。旧表结构会过期，翻了也白干。

细则（表头、邮件样例、邮箱参数）：`references/` 与基建库 `project-foundation`（安装后与 Skill 并列的 `project-foundation`，不是 Skill）。

它干什么

然后用脚本打印的清单回答用户。每条看 `status`：

| status | 你怎么说 |
|--------|----------|
| `done` | 办成了什么，归档在哪 |
| `skipped_duplicate` | 这封已经在某个归档夹，没有再办 |
| `archived_needs_you` | 文件已归档，但这件事还要用户拍板（把 `note` 说出来） |
| `needs_you` | 原件还在待处理里。回信要先读最新一段，看不准就问用户。确认后再用下面的 `dispatch_mail`，然后**再跑一次**本脚本，让它把已归档的原件拿走 |

## 已定产品原则（必须遵守）

1. **主交付**：结构化数据（`.skill/schedule.json`）。需要可视化时用时间线 HTML，**视觉必须遵守** `presentation.md` §4（禁止糙默认模板）。
2. **完成时点语义**：关键节点回答「何时完成（可请款）」。机器可留 `window_start`/`window_end`，**对齐与口头汇报一律以 `window_end` 为准**。
3. **对人默认旬粒度**：`YYYY年M月上/中/下旬`；JSON 仍存 ISO 日。
4. **时间线只有一份给人看**：`项目档案/00_进度计划/关键节点时间线.html`（另写 `.skill/critical_nodes_timeline.html` 同内容）。**禁止**再写采购包目录下的时间线 HTML。
5. **进度入口**：先认附件格式再转换；`.mpp`/XML 经 `mpp-to-excel` → CSV；已是机读 csv/xlsx 可直接进本 Skill。人看版 `*_project_view.xlsx` 按下面输入表处理。
6. **低置信须确认**：吃不准就 `pending` / `needs_confirm`，不静默当定稿。
7. **不准用字典冒充理解**：任务名各异；用上下文推理，关键词表最多当联想，不能当唯一判决。
8. **总包 ≠ 抽象项目级**：公共节点 `package_name=总包`（新写入禁止 `_project`；旧数据可读）。各采购包只挂请款相关节点。包级「验收」默认对齐总包/客户验收前后。

## 输入（先认格式，再进本 Skill）

**不是「只能读 CSV」，也不是「默认一定是 MPP」。**  
正确顺序：**先判断附件是哪种进度** → 需要时转成机读表 → 再推理关键节点。

| 认出来的格式 | 怎么处理 |
|------|------|
| 已是机读任务表（`.csv` / 扁平 `.xlsx`，第 1 行是「任务名称/开始/结束…」） | **直接**给本 Skill 读 |
| `.mpp` / Project XML | 先跑 `mpp-to-excel` → 得到 `*_schedule.csv`，再用 CSV |
| 普通粗表 Excel（有任务名+日期列，但不是本仓库产出的甘特壳） | 可先走 `mpp-to-excel` 规范化成 CSV，或 Agent 直接读 xlsx |
| **人看版** `*_project_view.xlsx`（第 1 行像「项目:…」，右侧是甘特色块） | **不是源表**。优先找同目录 `*_schedule.csv`；没有则回到原始 `.mpp`/任务表，**禁止**把 project_view 当源硬转 |

最低列（机读表）：任务/里程碑名称、开始、结束；可选采购包/专业。  
表头约定见 `<skills-root>/project-foundation/references/schedule-csv-schema.md`。

采购包清单：Tracker CSV，或对话/JSON 中的包名+类型。

## 工作流（Agent 主路径 · 必须遵守）

1. 确认项目根；收集进度附件与采购包列表（含 `package_type`）
2. **先认进度格式**（见上表）：该转 CSV 的先转，确认手里是机读任务表
3. 若源是 `.mpp` / Project XML（或需规范化的粗表）：先执行 `mpp-to-excel`，再用 `*_schedule.csv`
4. **阅读**进度表全文（或足够上下文）：搞清总包锚点、各包粗条/细节点、中英混写含义——**先理解**
5. 阅读 `node-taxonomy.md`、`matching-rules.md`、`presentation.md`（若尚未加载）
6. **推理**并整理 `critical_nodes` + `pending`（按包类型模板；完成时点用 `window_end`；依据写进 `basis`；公共节点挂「总包」）
7. **落盘**：调用 `write_critical_nodes.py`（校验 + 写入；可选 `--write-md` / `--write-timeline`）
8. 汇报：节点数、`inferred` 数、`pending`；对人日期用旬；强调**完成时点**
9. 汇报完即停。系统内后续见编排说明书

怎么用

你说看现金流、这个月要付多少，它只出预测表。建包或请款办完，它不会自己跟着算，除非你明确要看。

它干什么

它把各包的付款条件、完成日、已经请过的、变更里已确认的金额拼在一起，按月算出以后要付的钱。变更的增量加在最后一笔。完成日再加 30 天，算钱离开账户的那个月。不算收入。缺日期或缺金额就标出来问你。

什么时候用

你问现金流、资金计划、按月要花多少。建包或请款刚办完，不要自动抢着重算，除非你明确说要看预测。

你会碰到的问题

它会把预测写回请款或变更吗？

不会。只读状态表、卡片、进度和变更台账。

变更加在每一笔上吗？

不加。只加在最后一笔。已取消的变更不算。

为什么不是完成当月就出账？

默认滞后 30 天。你有指定天数或手工改期，按那个来。

做成了长这样

  • 项目根有一张现金流预测表，能按包、按月看。
  • 缺的日期和金额被标出来，没有被编成一个整数。
  • 采购包状态表、卡片、变更台账和跑之前一样。

# 现金流预测

一句话：**只读**各采购包合同付款条件 + 进度完成日 + 已付账 + 已确认变更，拼出**按月供应商出账预测**。边界见下面「状态口径」。

**全局原则**：先理解再处理（见 `skill-orchestration`）——日期与金额缺一项就进 `pending`，禁止手猜合同额或进度。

## 状态口径（对人）

| 原则 | 做法 |
|------|------|
| **只看出账** | 供应商付款；不算苹果/JLL 收入；不对接银行/ERP |
| **变更挂尾款** | Change Log「最终确认金额」合计只加在**最后一笔**付款节点（预测用；不读「是否请款」；跳过已取消） |
| **已确认变更列随变更走** | Excel「已确认变更」每次重算：直接读 Skill 3 的 Change Log。变更台账**不加**请款状态 |
| **出账滞后 30 天** | 完成锚点日 + 30 天 = 预计钱离开账户的月份 |
| **只读上游** | 不改 Tracker、card-data、Change Log |
